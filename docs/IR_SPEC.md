# IR Spec v1

Intermediate contract between Python exporter (Pytorch) and C++ runtime. The exporter
takes advantage of the shapes and metadata of the Pyotch model and writes them into
the IR; the C++ parser simply reads and validates rather than infers the structure.

`python/export_ir.py` always produces two files:
| File          | Role                                                                |
|---------------|---------------------------------------------------------------------|
| `graph.json`  | structure — nodes, shapes, and the weight manifest. Small, diffable.|
| `weights.bin` | contiguous little-endian float32 payload, 64-byte-aligned sections. |

A third file, `graph.txt`, is the textual rendering of `graph.json`. It is
generated by the exporter and reproduced byte-for-byte by the C++ `format_graph()`.

---

## 1. Model

Three `Linear` layers with `ReLU` after the first two, raw logits out. No output activation
function.

```
input [B,784] -> fc1 [128,784] -> relu1 -> fc2 [64,128] -> relu2 -> fc3 [10,64] -> logits [B,10]
```

Weights use **named module attributes** (`fc1`/`fc2`/`fc3`), not `nn.Sequential`. Only
named attributes produce `state_dict` keys of the form `fc1.weight`, which is what
`getWeight("fc1.weight")` resolves.

### Naming convention

| Type | Form | Examples |
|---|---|---|
| Weight tensor | `{layer}.{weight,bias}` | `fc1.weight`, `fc3.bias` |
| Activation tensor | `{node}.out` | `fc1.out`, `relu2.out` |
| Graph input | `input` | — |

The `.out` suffix keeps the activation namespace disjoint from the weight namespace. Node
names (`fc1`) and their output tensor names (`fc1.out`) are differentiable for the structural
verification later.

## 2. Op set

Strictly, closed enum. Anything outside it is a malformed IR, not an extension point.

| Op | Weights | Notes |
|---|---|---|
| `Linear` | yes | `y = x @ Wᵀ + b` |
| `ReLU` | no | elementwise `max(x, 0)` |
| `LinearReLU` | yes | fused; in the vocabulary from day one |

`LinearReLU` is accepted by the parser from v1 but is not emitted by the exporter — the
fusion pass introduces it later by rewriting the graph. The parser does not change when
that happens.

**There is no `Flatten` op.** The graph input is already flattened to `[B, 784]`; the
`[1,28,28] -> [784]` reshape is host-side responsibility, outside the graph. `golden/input.npy` is stored flattened so the runtime can feed it directly.

## 3. Layout conventions

- **Row-major** (C order) throughout.
- **Weight shape is `[out_features, in_features]`** — the same layout `torch.nn.Linear`
  already uses. The exporter must never transpose, and neither must any kernel.
- **Bias shape is `[out_features]`.**
- **dtype is `float32`**, little-endian, written as the string `"float32"`.

### Field rules

**Top level.** `ir_version` is `1`. `alignment` is a power of two, `64` in v1.
`weights_total_bytes` is the exact size of `weights.bin` including tail padding.
`weights_sha256` is optional; when present the loader may verify it.

**`graph_inputs[]`.** `shape` uses `-1` as the **runtime batch sentinel** — the batch
dimension is not fixed at export time. `features` is the trailing (non-batch) dimension,
duplicated as a plain int so consumers never have to interpret the sentinel to size a
layer. `-1` must never reach an element-count computation.

**`weights[]` — the manifest.** Entries appear in the same order they were written to
`weights.bin`. `byte_offset` is the section start, always a multiple of `alignment`.
`byte_len` is the **unpadded** payload length, exactly `prod(shape) * 4`. Padding lives
strictly *between* sections and is never covered by any `byte_len`. Sections never
overlap. Names are unique.

**`nodes[]`.** Ordered; execution is in list order. Each `output` is written exactly once
(SSA), and every name in `inputs` must be a graph input or the output of an *earlier*
node — forward references are invalid.

`inputs` holds **activation tensors only**. Weight references live in the separate
`weight` and `bias` keys. This keeps the dispatch loop honest: everything in `inputs` is
in the runtime tensor map, and nothing else is.

`weight_shape`/`bias_shape` deliberately duplicate the manifest. That redundancy is the
point — the loader cross-checks node against manifest and fails at load time rather than
producing garbage math at execution time.

Ops without weights **omit** `weight`, `bias`, `weight_shape`, and `bias_shape` entirely.
They are absent keys, not empty strings. The loader rejects their presence on a
non-weighted op and their absence on a weighted one.

`in_features` must equal the producing node's `out_features` (or the graph input's
`features` for the first node).

**`outputs[]`.** Tensor names, each of which must be some node's output. Shapes are not
repeated here; they already live on the producing node.

## 5. `weights.bin`

No header, no magic number — a bare concatenation of aligned sections. Integrity comes
from `graph.json` instead: `weights_total_bytes` is mandatory and `weights_sha256` is
optional, which turns "the two files desynced" from an unfalsifiable claim into a
load-time assertion.

Write algorithm, and the definition of the offsets:

```
offset = 0
for each weight in exporter order:
    pad    = align_up(offset, 64) - offset      # zero bytes
    offset += pad
    byte_offset = offset
    byte_len    = prod(shape) * 4               # unpadded
    offset += byte_len
tail_pad = align_up(offset, 64) - offset        # so total size % 64 == 0
```

The **tail padding is load-bearing**: it makes the total size a multiple of the alignment,
which is what allows the C++ side to use `std::aligned_alloc` legally.

The buffer must be allocated 64-byte-aligned. A 16-byte-aligned base (what `operator new`
gives on macOS) would place a `byte_offset % 64 == 0` section at a 16-aligned address, and
the entire alignment contract would be void before any SIMD load ever saw it.

> Note: with the pinned dims (784/128/64/10) every section except the last is *naturally*
> 64-aligned, so only the tail pad is exercised by the real model. Interior padding must
> be covered by a synthetic test or it will break silently the first time an op has an odd
> feature count.

## 6. `graph.txt`

Canonical rendering of `graph.json` from the exporter and reproduced by the
C++ `format_graph()`. Verifiable check to compare if printGraph output matches the
exporter's node list.

```
graph ir_version=1 alignment=64 weights_file=weights.bin weights_total_bytes=437568
input name=input dtype=float32 shape=[-1,784] features=784
weight name=fc1.weight dtype=float32 shape=[128,784] byte_offset=0 byte_len=401408
weight name=fc1.bias dtype=float32 shape=[128] byte_offset=401408 byte_len=512
weight name=fc2.weight dtype=float32 shape=[64,128] byte_offset=401920 byte_len=32768
weight name=fc2.bias dtype=float32 shape=[64] byte_offset=434688 byte_len=256
weight name=fc3.weight dtype=float32 shape=[10,64] byte_offset=434944 byte_len=2560
weight name=fc3.bias dtype=float32 shape=[10] byte_offset=437504 byte_len=40
node index=0 op=Linear name=fc1 inputs=[input] output=fc1.out weight=fc1.weight weight_shape=[128,784] bias=fc1.bias bias_shape=[128] in_features=784 out_features=128
node index=1 op=ReLU name=relu1 inputs=[fc1.out] output=relu1.out in_features=128 out_features=128
node index=2 op=Linear name=fc2 inputs=[relu1.out] output=fc2.out weight=fc2.weight weight_shape=[64,128] bias=fc2.bias bias_shape=[64] in_features=128 out_features=64
node index=3 op=ReLU name=relu2 inputs=[fc2.out] output=relu2.out in_features=64 out_features=64
node index=4 op=Linear name=fc3 inputs=[relu2.out] output=fc3.out weight=fc3.weight weight_shape=[10,64] bias=fc3.bias bias_shape=[10] in_features=64 out_features=10
```

Format rules — deliberately trivial, because two renderers in two languages have to agree:

- Line order: `graph`, then every `input`, then every `weight`, then every `node`, then
  every `output`.
- Space-separated `key=value` pairs. **No column padding** — alignment padding is where
  cross-language renderers diverge.
- Shapes and input lists render as `[a,b]`: brackets, comma-separated, no spaces.
- `ReLU` node lines omit the four weight keys, matching §4.
- Integers are plain decimal. `-1` renders as `-1`.
- LF line endings, exactly one trailing newline per line, no trailing whitespace.

## 7. Golden tensors

`python/golden_oracle.py` reads `graph.json` and dumps one `.npy` per node, **named after
`node["output"]`**. Validation then iterates the node list, so the two sides cannot drift
apart by construction.

| File | Shape |
|---|---|
| `golden/input.npy` | `[10, 784]` |
| `golden/labels.npy` | `[10]` (int32) |
| `golden/{fc1,relu1}.out.npy` | `[10, 128]` |
| `golden/{fc2,relu2}.out.npy` | `[10, 64]` |
| `golden/fc3.out.npy` | `[10, 10]` |

The probe batch is MNIST test samples `0..9`, fixed. Goldens are generated **on CPU**, not
MPS — different accumulation orders across devices are a variable worth eliminating before
debugging a kernel, not during.

## 8. Validation policy

FP32 paths compare against goldens with `numpy.allclose` semantics:

```
|actual - expected| <= atol + rtol * |expected|      rtol = 1e-4, atol = 1e-6
```

`expected` is the reference — the relative term scales by it, so argument order matters.
NaN never passes.

## 9. `weights/*.npy`

The exporter also dumps each weight as a standalone `.npy`. These are **validation
fixtures only** — never the runtime loading path, which is always `weights.bin` plus the
manifest. They exist so a test can compare `getWeight("fc1.weight")` element-for-element
against an independently-written file, which catches offset, endianness, transpose, and
padding-arithmetic bugs in a single assertion.
